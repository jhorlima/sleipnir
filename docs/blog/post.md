## 1. The question

How fast do different query engines ingest, transform and serve the same data when you give them the same hardware, the same tables and the same semantic layer? And what does each acceleration trick (materialized views, pre-aggregations, compaction) actually buy?

## 2. Choosing the stack

| Layer | Choice | Why |
|---|---|---|
| Object storage | RustFS | S3-compatible and light; MinIO's community edition is no longer maintained. |
| Catalog | Lakekeeper (Iceberg REST) | Light, REST-native, needs only Postgres. |
| Ingestion | DuckDB | Reads CSV very fast; Airbyte needs Kubernetes and ~8 GB just to idle. |
| Transformation | dbt on Trino and Spark (Postgres as baseline) | Same project, several engines. |
| Readers | StarRocks, Trino, DuckDB, Postgres | One writer, many readers on the same files. |
| Semantic layer | Cube + Cube Store | Measures, dimensions and pre-aggregations over every engine. |
| Runtime | Docker Compose with profiles and resource limits | Swarm or Kubernetes add nothing for a single node. |

### 2.1 Compatibility drove two choices: dbt Core 1.x and Iceberg v2

Both "newest" options were on the table and both lost to engine compatibility (October 2026):

- **dbt Core v2** (Rust, built on the Fusion engine) was still in alpha. Spark and DuckDB adapters were in beta, but there was no v2 adapter for **Trino** or **Postgres**. We stayed on **dbt Core 1.12 + dbt-trino 1.10** so that every engine runs the same project.
- **Iceberg v3** (deletion vectors, row lineage, variant) was supported by Spark 4.1 + Iceberg 1.11 and by DuckDB 1.5.3, but **Trino** could only read v3 experimentally (no row-level writes or `OPTIMIZE`), **StarRocks 4.1** rejected tables containing deletion vectors, and catalog support was unconfirmed. Since Trino is the main writer and StarRocks the main reader, we stayed on **Iceberg v2**.

Both are listed as "revisit later"; the benchmark can be re-run when the ecosystem catches up.

## 3. Designing a fair benchmark

- One engine under test at a time; never two transformations in parallel.
- Same CPU/memory limits per profile (S, M, L) for every engine; same dbt thread count everywhere.
- Every query result is checked (row count + checksum) against a DuckDB reference before its timing counts.
- Each transformation step (dbt model, microbatch batch, maintenance operation, MV refresh) is timed on its own.
- Maintenance runs as a post-hook in normal use, but is switched off inside measured runs and timed separately.
- A single run must fit in 10 GB of object storage, so it can be repeated on a free-tier bucket (Cloudflare R2).
- Locally there is no such limit: if ingesting the 10 GB scale is fast and only bounded by download speed, the local scale grows to ~20 GB or ~30 minutes of ingestion, whichever comes first. Numbers from different scales are never compared.

## 4. The data

- **NOAA GHCN-Daily** — daily weather observations; the medallion story (bronze → silver → gold).
- Duplicates are created on purpose: incremental batches overlap by 7 days and ~1% of rows are re-emitted with revised values, so deduplication and incremental strategies have real work to do.
- **TPC-H** (generated by DuckDB) — standard queries for comparability. Results are derived from TPC-H and not comparable to published TPC-H results.

## 5. Building it — lab notebook

### Phase 0 — spec

- Wrote the full spec before any code: architecture, suites B1–B6, storage budget, decisions and open questions turned into spikes (V1–V9).
- Lessons carried over from previous Cube work, written as rules:
  - Cube's SQL drivers send DECIMAL to Cube Store as `Decimal(18,5)` — rollup sums silently lose precision. Cast rollup measures to DOUBLE.
  - Without its materialized view, StarRocks silently falls back to the base table — so every accelerated query is validated with `EXPLAIN`.

### Phase 1 — MVP lakehouse

- **Spike V4 — does dbt-trino support microbatch?** Yes, since dbt-trino 1.9.0. On Trino it is a `DELETE` + `INSERT` per batch filtered on `event_time` (it ignores `unique_key`), so each batch creates two Iceberg snapshots and position-delete files. Prediction: microbatch will need compaction more than any other strategy.
- **Gotcha:** Trino renamed the native S3 switch from `fs.native-s3.enabled` to `fs.s3.enabled`.
- **Storage and catalog up** (RustFS 1.0.1, Postgres 18.6, Lakekeeper 0.14.0, Traefik 3.7). `make init` creates the bucket and the Iceberg warehouse and is safe to run twice.
- **Gotchas:** RustFS answers its bare root with an S3-style 403 (the console lives under `/rustfs/console/`, so the proxy redirects). RustFS has no STS, so the Lakekeeper warehouse uses the `s3-compat` flavor with `sts-enabled: false` — engines either use remote signing or their own keys.
- **Spike V1 — can DuckDB write Iceberg through the REST catalog?** Yes: DuckDB 1.5.6 creates and appends partitioned Iceberg v2 tables through Lakekeeper (~2–6M rows/s on a 2M-row sample, unthrottled). The catch: DuckDB does not support remote signing and the local warehouse has no STS, so vended credentials fail (`404`). It needs `ACCESS_DELEGATION_MODE 'none'` plus a static S3 secret. Also: DuckDB defaults to snappy, not zstd, and names partition fields `identity__batch_id_<id>`.
- **Trino 483 on the REST catalog.** Single node, heap at 75% of the container limit, query memory left at Trino's defaults so it scales with each profile (M: 8 GB container → 6 GB heap → ~4.2 GB query pool). Iceberg v2 + Parquet + ZSTD by default.
- **Gotchas:** behind Traefik the Trino UI answered `406` until `http-server.process-forwarded=true` (Trino rejects `X-Forwarded-*` headers by default). Trino has no remote signing for Iceberg REST, so it uses static S3 keys like DuckDB. Mounting a catalog folder hides the image's built-in `tpch`/`tpcds` catalogs.
- **Cross-engine check:** Trino reads the partitioned table DuckDB wrote, including DuckDB's partition field name, and prunes partitions on `_batch_id`.
- **Same I/O path for every engine.** Lakekeeper's S3 warehouses default to remote signing. Spark and PyIceberg would have silently signed every request through the catalog, while Trino, DuckDB and StarRocks use static keys. That is two different I/O paths behind one catalog, and the read numbers would not be comparable. Remote signing is now off, and every engine uses the same keys.
- **Small hardening from the official examples:** a TCP Postgres healthcheck (the socket answers while the init server is still running), explicit catalog connection pools, `RUST_LOG=info`, and a hard delete profile.
- **First year ingested (GHCN 2025).** 1.31 GB of CSV (168 MB gzipped), 36.3 M source rows, cut into 12 monthly batches with a 7-day overlap and ~1% revisions: 43.97 M bronze rows (+17% duplicates), 116 MB of Parquet/ZSTD in source order. DuckDB inserted each batch in 0.47–0.79 s (4.8–7.4 M rows/s) on the M profile (4 CPU / 8 GB), with each batch committed to Iceberg in one go.
- **Design change:** the first cut used a 30-day overlap on monthly batches, which made 47.6% of bronze duplicates. Each batch repeated almost a whole month. A 7-day overlap still gives deduplication real work, and it keeps bronze close to the source size so more years fit the budget.
- **Gotcha:** a whole-table `GROUP BY` on the natural key exceeds Trino's default per-query memory on the M profile (~1.8 GB). Deduplication has to work per batch window, or Trino needs spill-to-disk.
- **Gotcha:** sorting rows before writing halved the Parquet size (7.9 vs 16.5 MB per batch). Bronze keeps the source order to stay a faithful copy; sort order becomes a layout variable for B6.
- **Gotcha:** with Docker Desktop's VM at 8 GB, Trino on the M profile (8 GB limit) was OOM-killed (exit 137) while an image build and the infra ran beside it. Container limits are not reservations, so the VM needs room for the engine profile plus ~3 GB of infra. For the L profile, give the VM ≥ 16 GB.
- **dbt on Trino, bronze → silver → gold.** 6 models, 32 data tests + 2 unit tests. The full build takes 64.7 s on profile M (silver 42.7 s, fact 9.0 s), and an incremental build with nothing new takes 13.3 s. Silver keeps 28.6 M rows from 34.6 M core-element bronze rows (−17%: overlap duplicates plus QC). Lakehouse total: 0.23 GB.
- **First strategy numbers (silver, one run each):** from scratch, merge 52.8 s, delete+insert 52.6 s, microbatch 26.3 s (12 monthly batches). Loading one new batch: 6.95 s, 7.41 s and 5.3 s. All three produce identical rows and `sum(value)`. Default: delete+insert, because its window comes from the data. dbt's microbatch follows the wall clock, so on historical data it needs explicit event-time bounds.
- **Gotcha:** dedup with `ROW_NUMBER() = 1` failed on profile M even with spill-to-disk on. Trino rewrites it into a TopNRanking operator, which cannot spill. `optimizer.optimize-top-n-ranking=false` fixes it, and it is recorded as a non-default engine setting.
- **Gotchas:** GHCN publishes SNOW/SNWD in mm, not tenths. `dbt_utils.fewer_rows_than` breaks on Trino, and `dbt_utils.recency` compares to the wall clock (useless for historical data), so both became singular tests. The `tmax >= tmin` test warns on 4 rows created by the simulated revisions, which is exactly what it should catch.
- **Cube 1.7.50 on Trino.** One template per cube, rendered per data source. All ten questions answer through the REST API, and Q1–Q3 match direct Trino SQL exactly (Q3 differs only at ~1e-12 from float summation order). Every modern pattern worked on Trino: `approx_percentile`, a nested aggregate through a `sub_query` dimension, share of total with multi-stage `grain`, `time_shift` period-over-period and a 7-day rolling window.
- **Gotcha:** Trino's `approx_percentile` is not deterministic (the same median came back as 627–645 across runs), so percentile queries get a 5% tolerance instead of an exact checksum.
- **Gotchas:** Cube requires a `default` data source even when no cube uses it (here, an in-memory DuckDB). Cube's Jinja auto-escapes strings, so generated names rendered as `"trino"_stations` until helpers returned `SafeString`. The official images ship without curl, so the healthchecks use `node` fetch and bash `/dev/tcp`.
- **Phase 1 accepted.** From `make clean` to Cube answering the questions, everything ran in one go in about 3 minutes: ingest 12 batches → dbt build (39 tests passing, 1 expected warning) → storage report (0.23 GB, well under the 10 GB budget) → Cube Q1–Q6.
- **Too little data to benchmark.** At 0.23 GB, fixed overheads (planning, catalog round trips, JVM, Cube) and caches dominate, cold and warm would look the same, and there is nothing for compaction to fix. Phase 2 therefore starts by scaling up: GHCN 2010–2025 for the 10 GB scale (lakehouse ~3.5 GB estimated) and more years for the local scale.
- **Explicit over generated.** The first Cube model rendered every engine's cubes from one Jinja template, which made it hard to read and hit an auto-escaping gotcha. It now uses Cube's native `extends`: members are written once in `base_*` cubes, and each engine file (6 to 34 lines) shows only what differs (table path, percentile function, joins). Rule of thumb adopted for the whole repo: abstract only when copies must stay identical for correctness, the difference is small, and the tool has a native mechanism.
- _(next: phase 2 — bigger data first, then the benchmark harness, Spark and Postgres as writers, StarRocks/DuckDB/Postgres as readers, TPC-H, acceleration and layout suites)_

### Phase 2 — benchmark

- **Scale `r2`: GHCN 2010–2025.** 16 yearly files, 2.81 GB gzipped. They become 192 monthly batches (3.36 GB) and 741.9 M bronze rows. After one writer's silver and gold, the lakehouse holds 3.75 GB: bronze 1.98, silver 1.02 (455.2 M rows), gold 0.75 (190.2 M fact rows). That is 16× phase 1 and still leaves room for TPC-H under the 10 GB budget. The estimate made before downloading (lakehouse ~4.0 GB, batches ~3.6 GB) was close.
- **Batches are now gzipped CSV.** Uncompressed, the batches would take ~25 GB of landing space; gzipped they take 3.4 GB. The worry was that DuckDB would ingest slower, since it cannot split a gzip stream across threads. It did not: B1 ran at 5.24 M rows/s on profile M (0.65–1.13 s per batch, 142 s for all 192), the same as phase 1. Writing the batches is the slow part (~1 min per year, single-threaded gzip), and it stays outside the measurement because it stands in for the source system.
- **Gotcha: the from-scratch build stopped fitting in one query.** On profile M, Trino ran the silver dedup (`ROW_NUMBER` over ~740 M rows) for 9 minutes and failed with `EXCEEDED_SPILL_LIMIT` at 10 GB of spill. The whole-table uniqueness test fails the same way. The fix was already in the project: build from scratch one month at a time with dbt's microbatch (`make dbt-backfill`). Each month takes 2–9 s. Silver took 506 s in total, the fact table 267 s and the monthly aggregate 244 s. Later incremental runs keep using delete+insert. A year-by-year check found zero duplicate keys.
- **Gotcha: in a microbatch run, dbt runs the post-hook after every batch.** With maintenance as a post-hook, a 192-month backfill would compact and expire snapshots 192 times. The backfill turns the hook off and runs maintenance once per table at the end, about 2 s each.
- **Gotcha: the laptop went to sleep in the middle of a run.** Two months of the backfill failed with Trino's `ABANDONED_TASK` after 20 and 7 minutes. Trino was fine. macOS had gone into idle sleep (`pmset -g log`), the Docker VM froze, and when it woke up the coordinator had lost track of its tasks. The clue was in the query IDs: they lagged the log clock by 27 minutes, because Trino stamps them from a monotonic clock that stops while the VM is suspended. Long runs now go under `caffeinate -i`, and the harness will refuse to measure without it.
- **Gotcha: four dbt threads OOM-killed Trino on an 8 GB VM.** Four full-scan tests over 455 M rows at once pushed Trino's 6 GB heap plus native memory and the infra past the VM's 7.75 GiB, and the kernel killed it (exit 137). The tests pass with one thread. Before measuring on profile M, the Docker VM gets ≥ 12 GB.
- **More room, no swap.** The Docker VM now has 8 CPUs, 16 GB and 2 GB of swap, so profile M (8 GB) has room beside the infra. Docker lets a container with only a memory limit swap as much again on top of it. An engine short on memory would then crawl through swap instead of failing, and the slowdown would end up in the numbers without anyone noticing. Engine containers now set `memswap_limit` equal to their memory limit.
- **Uniqueness, tested where it can break.** The whole-table key test on silver no longer fits Trino's spill limit. It now checks only the dates the latest run can have written: the newest month plus twice the batch overlap. That is enough because delete+insert, merge and microbatch all replace whole dates, so a duplicate can only appear where a run wrote. A year-by-year macro (`assert_unique_by_year`, ~4 s per year) still checks the whole table after a backfill, outside the measured steps. With the VM at 16 GB, the full test suite passes with 4 threads in 171 s (467 s with one thread).
- **Data quality at this scale:** 32 tests pass. The `tmax >= tmin` warning now flags 98 rows from the simulated revisions (4 in phase 1).
- **Spike V2 — Trino materialized views on a REST catalog?** No. Trino 483 answers `createMaterializedView is not supported for Iceberg REST catalog`, and the same code is on master; plain views work. B5b therefore becomes an "MV-equivalent table": a dbt `table` model with the same SQL as the StarRocks MV, rebuilt as the measured refresh, and Cube reads it by name. Trino would not rewrite queries to an MV anyway, so Cube had to point at it either way.
- **Spike V13 — DuckDB inside Cube.** Cube 1.7.50 embeds DuckDB 1.5.5 in its own Node process, one patch behind the 1.5.6 used for ingestion. Extensions load from env vars, but attaching the Iceberg catalog needs a small `driverFactory` in `cube.js`, the one exception to plain config. The fairness catch: Cube's DuckDB shares the Cube container's CPU and memory instead of getting an S/M/L engine profile like the other readers, so its numbers need that label or a matching limit. Two gotchas from the driver source: a failing init SQL is logged and skipped, then cached until Cube restarts, and extensions are downloaded on every start.
- **Spike V9 — which Cube questions can Cube Store answer?** From the docs: the share of total (Q9, plain sums) and the year-over-year delta (Q10, at exactly country × month) should match rollups. Percentiles (Q7) only match a rollup at their exact grain and with an explicit granularity. The nested median through a `sub_query` dimension (Q8) has no documented support. The open question to prove first is whether a query with a date range but no granularity matches a rollup at all.
- **Spike V3 — will StarRocks rewrite queries to a join MV over Iceberg?** On paper, yes: StarRocks 4.1.6 documents async MVs on Iceberg REST catalogs with automatic join and aggregate rewrite. There are three catches to prove locally. Questions that join fewer tables than the MV need "view delta join", which relies on key constraints that may not be declarable on Iceberg tables. Partition-level change detection is documented only for Iceberg v1, and our tables are v2. The metadata cache can make the first query after a refresh miss the MV. One open bug decided a setting before any test: union rewrite on Iceberg's time-transformed partitions can silently drop rows (#79345), so the benchmark session turns union rewrite off.
- **DuckDB as a Cube data source, working.** Cube's embedded DuckDB reads the Iceberg gold tables through Lakekeeper. All ten questions answer, and Q1–Q3 match a direct DuckDB query exactly (Q3 within 7e-16). At Cube's default limits (1 CPU / 1 GB, DuckDB at 512 MB), the nested median (Q8) runs out of memory at scale r2. That settles the fairness rule: when DuckDB is measured through Cube, the Cube container gets the same profile limits as the other engines, and DuckDB gets 75% of that memory. Node's overhead then comes out of DuckDB's budget, and the results will say so.
- **Spark 4.1 joins as the second writer.** Spark 4.1.3 + Iceberg 1.12.0 run as a single-JVM Thrift Server sized from the profile (`local[4]`, 6 GB driver on M), and dbt-spark 1.11.0 talks to it through PyHive. The same dbt project built 2025 on Spark in 87 s with microbatch (silver 52 s for 12 months). The tests pass and flag the same 4 `tmax < tmin` rows Trino flagged in phase 1. Trino reads the Spark-written tables directly.
- **Gotchas porting the project to Spark:**
  - dbt-spark rejects a source whose `database` differs from its schema, so the bronze source no longer names the catalog.
  - dbt-trino does not ignore Spark's `file_format: iceberg`: it turns it into the table property `format` and the build fails. The project now sets `iceberg` for Spark and `PARQUET` for Trino.
  - On a table created earlier in the same run, dbt-spark picks the Hive `insert overwrite` syntax, which breaks the second microbatch batch. A small macro override fixes it.
  - PyHive always sends `USE default`, so an empty `default` namespace has to exist in the catalog.
  - Spark has no delete+insert strategy, so its default is merge.
  - Spark refuses to remove orphan files younger than 24 h, so its maintenance is not identical to Trino's. The difference is recorded with the B6 numbers.
- **Postgres moves to its own scale.** As a row store, Postgres needs ~65 bytes per row against Parquet's ~2.7. Scale r2 would take ~90 GB inside Postgres, more than the whole Docker disk. Postgres stays as the baseline, but on a `small` scale (2025 only, 44 M bronze rows, ~6 GB in Postgres), where every other engine also runs B2/B3. That way it is compared on the same data and never against a bigger scale.
- **StarRocks 4.1.6 joins as a reader.** It reads the same Iceberg tables through an external catalog, and its counts match Trino's (190,214,772 fact rows). Through Cube, Q1–Q3 match the DuckDB reference.
- **Gotchas setting up StarRocks:**
  - The all-in-one image starts the FE with an 8 GB heap by default, which alone would kill profile S. The heap is now 25% of the profile and the BE gets 62.5%. A query over the BE limit now fails with an error instead of taking the container down.
  - Cube's rolling 7-day window (Q5) does not run on StarRocks: Cube emits `WITH RECURSIVE`, which StarRocks 4.1.6 does not support.
- **Spike V3, proved: StarRocks rewrites to a join MV only when the query joins exactly the same tables.** A wide MV (fact × station × date) served the hand-written queries that join all three tables, with identical results. It served none of the SQL that Cube generates, because Cube joins only the cubes a query touches. Declaring primary and foreign keys on the Iceberg tables did not unlock "view delta join". The fix comes from a production pattern: one MV per table (a plain copy of every column, no joins, no aggregation). StarRocks then swaps each table scan for its MV, whatever joins the query has. Cube keeps reading the plain marts, StarRocks does the rewriting, and no data is duplicated across MVs. Aggregated MVs come later, if StarRocks rewrites Cube's queries to them.
- **MV refresh, measured.** Refreshing the wide MV took 540–589 s for 190 M rows and 192 monthly partitions. It needs a one-hour `query_timeout`, because the synchronous refresh statement is killed at 300 s. Create the MV `DEFERRED`, or creating it already fills it and the first measured refresh does nothing. After the refresh the BE compacts for ~10 minutes, and queries during that window fail on memory, so reads wait until the container's CPU drops. The MV takes 4.8 GB on StarRocks' local disk, outside the bucket.
- **Cluster by, Iceberg style.** Iceberg has no `CLUSTER BY`, but it has a table sort order: Trino's `sorted_by` property, Spark's `WRITE ORDERED BY`, and z-ordering through Spark's `rewrite_data_files`. Phase 1 already showed that sorting before writing halves the Parquet size. B6 adds sort order to its matrix, with `fct_weather_daily` as the test table, to see whether it also speeds up reads through better file pruning.
- **Postgres as the small-scale baseline, working.** DuckDB copies the 2025 bronze batches from Iceberg into a dedicated Postgres (44,684,689 rows, equal to the Iceberg count), and the same dbt project builds silver and gold there. The tests pass with the same 4 `tmax < tmin` warnings as Trino and Spark, and Cube answers all ten questions.
- **The row store's price, measured.** 2025 takes 0.23 GB as Iceberg/Parquet and 8.15 GB inside Postgres (bronze 5.08, silver 2.20, gold 0.86): about 35× more. On top of that, Postgres keeps up to `max_wal_size` (8 GB) of WAL, so its volume reached 16.8 GB for a 44 M-row year. That is why Postgres only runs on the small scale.
- **Gotchas porting the project to Postgres:**
  - `cast(x as double)` does not exist in Postgres (it is `double precision`), so the models now cast through a small dispatched `type_double()` macro.
  - dbt-postgres runs each microbatch batch as a merge and refuses microbatch without a `unique_key`, so on Postgres the natural key is passed.
  - `VACUUM` cannot run inside the transaction that wraps dbt post-hooks, so the Postgres maintenance commits first.
- **Gotcha: NULLs first or last?** Comparing Postgres to DuckDB through Cube, the top 20 stations by precipitation (Q3) came out completely different. In a `DESC` sort Postgres puts NULLs first, while DuckDB, Trino and StarRocks put them last, so Postgres's top 20 were stations with no rain recorded at all. The question now filters on stations that have precipitation, for every engine. The checksum gate caught it before any timing counted, which is exactly what it is for.
- **TPC-H at SF8.** DuckDB's `dbgen` writes TPC-H straight into Iceberg: SF1 takes 0.227 GB with zstd, so SF8 (1.875 GB, 48 M lineitem rows, generated in ~65 s) is the largest that fits the 2 GB slice of the budget. All 22 queries return identical results on DuckDB, Trino and StarRocks. The dialect edits were small: `substr` instead of `substring(... FROM ... FOR ...)` in Q22, and grouping by the column instead of its alias in Q15. One trap: Q11's threshold must be scaled as `0.0001 / SF`, as the spec says, or it returns nothing at SF8.
- **One MV per table, proved.** With a plain-copy MV for each gold table, StarRocks replaced every Iceberg scan in every query it can run, including all the SQL Cube generates, and the results matched the base tables. It is also cheaper than the wide join MV: the fact refresh took 382 s instead of 540–589 s, and the MVs take ~1.3 GB after compaction instead of 4.8 GB. Two operational notes: compaction runs for ~25 minutes after a refresh, and afterwards the BE sits near its memory limit while idle, so StarRocks restarts before the first measured query (the MVs survive the restart). The nested median (Q8) does not fit StarRocks' memory on profile M, with or without MVs, and is recorded as a failure.
- **Spike V9, proved: Cube Store can take the multi-stage questions.** On Trino, rollups served Q2, Q3, the share of total (Q9, both stages) and the year-over-year delta (Q10, including the shifted 2024 stage), with results equal to the source. Percentiles (Q7) only hit a rollup when the query asks for a yearly granularity. The nested median (Q8) hit too, but it differs 4.6% from the source, close to the 5% tolerance. One doc claim did not hold: a date range without granularity does match a rollup, as long as every measure is additive.
- **Gotcha: Cube's result cache survives restarts.** It lives in the Cube Store volume, and two "baseline" answers came back from the day before. Every measured Cube request now sends `renewQuery: true`, and the volume is recreated before a full run, so a cold read really is cold.
- **The read harness is in.** B3 (direct SQL), B4 (through Cube) and the B5 gates run from a container on the compose network. For each query: restart the engine, 1 cold run, 1 discarded warm-up, 5 warm runs, a DuckDB checksum on every answer, and `docker stats` throughout. A first smoke run (not the benchmark) gave warm p50s of ~0.3 s for Trino direct, ~3.3 s for Trino through Cube, and ~0.12 s for StarRocks reading its MVs.
- **Gotcha: you have to really tell Cube not to cache.** In Cube 1.7.50, `renewQuery: true` still returned a cached answer in ~4 ms. Only `cache: "no-cache"` at the top level of the request forces Cube to re-run the query. With caching truly off, Cube adds a floor of ~3 s per query on Trino, even for a query that takes 0.3 s direct. That overhead is part of what B4 measures.
- **Gotcha: float noise in checksums.** Rounding to 2 decimals flipped on noise like 21.975 vs 21.974999999999998. The checksum now cuts at 9 decimals before rounding half up.
- **The layout suite (B6) is ready.** It changes one factor at a time over a copy of the fact table: file size, codec, yearly partitions, Trino's `sorted_by` and Spark's z-order. A validation run (not the benchmark) already points two ways. Sorting by station and date shrank the fact table from 0.73 GB to 0.38 GB, at 2.3× the write time, with reads unchanged. And with monthly partitions the files are only 2–4 MB, so the target file size knob probably does nothing; the partition grain matters more.
- **Gotchas building B6:**
  - A sorted CTAS of all 192 months runs out of writer memory on Trino profile M, so every variant is written one year per `INSERT`.
  - Spark's `rewrite_data_files` silently skips a partition that holds a single file. Z-ordering needs `rewrite-all`.
  - DuckDB cannot read Iceberg views, so each variant gets real copies of the dimension tables.
- **A rule for partitions, from B6.** Partition only when each partition is big (about 1 GB compressed for now, i.e. a few full-size files) and the filters line up with it. Below that, skip partitions or use coarser ones, and let a sort order ("cluster by") do the pruning through each file's min/max stats. The exception is a partition that serves the writes, like bronze by ingest batch or silver aligned to the delete+insert windows. Measure in bytes, not rows: 190 M rows of the fact table are only 0.38 GB, and monthly partitions held 2–4 MB each.
- **Sorted fact on both writers.** Trino's `sorted_by` sorts every write, including each microbatch month. Spark can only set `WRITE ORDERED BY` on a table that already exists, so its sort comes from the maintenance rewrite (`rewrite_data_files` with a sort strategy and `rewrite-all`, 103 s). Both facts now take ~0.39–0.40 GB with identical row counts and sums.
- **Gotchas rebuilding the layout:**
  - A microbatch backfill on an existing table only inserts. Changing a table's layout needs `--full-refresh`, or the old unsorted table silently stays.
  - The object store's 1 GiB memory limit was OOM-killed twice during hour-long runs. Trino reported it as "Unknown host rustfs", and once it slowed batches 20×. RustFS now gets 2 GiB. It is shared infrastructure, constant for every engine, so this does not tilt the comparison, but it would have quietly polluted a measured run.
  - The fact table's whole-table key test (190 M rows) also runs Trino out of memory on profile M. It now follows the silver pattern: a test on the latest window plus a year-by-year check.
- **B6, second round: does a sort order make partitions unnecessary?** No. A sorted table without partitions is as small as the partitioned one (0.375 GB), but queries filtered by period got 60–80% slower, because Trino can no longer skip whole months from the manifest. Sorting by date first compresses worse (0.52 GB). The first version of the partition rule ("only above ~1 GB per partition") did not survive the numbers and was rewritten.
- **Incremental or full refresh, model by model.** Bronze is append-only: each monthly batch is added and never rewritten. The big tables with a time axis (silver `ghcn_daily`, gold `fct_weather_daily` and the monthly aggregate) are incremental. Each run processes only the dates of the new batch, minus the overlap, with the engine's strategy (delete+insert on Trino and Postgres, merge on Spark). The small reference tables (stations, the two dimensions) are rebuilt in full every run, because it takes about a second and leaves no window to get wrong. Building from scratch is the exception: at this scale it goes month by month with microbatch, never as one query.
- **Gotcha: the object store gets tired.** After ~10 hours of benchmark traffic, RustFS sat at 1.5 of its 2 GiB and answered slowly. Spark's monthly batches went from 10 s to 100–500 s and then failed with S3 read timeouts. Trino had run on a freshly started RustFS. To keep the comparison fair, the object store now restarts before each engine's campaign.
- **Gotcha: the laptop slept again, between runs.** Each measured command ran under `caffeinate -i`, but that only holds while the command runs. In a quiet gap between two runs the screen turned off and the Mac went into idle sleep. The next run was launched into a sleeping machine, kept alive only by brief Power Nap wake-ups. The Docker VM froze and Trino abandoned its queries. The fix is a keep-awake app with a timer covering the whole campaign, gaps included.
- **Why the network is not in the numbers yet.** The scale is called `r2` because it fits Cloudflare R2's free tier, but every run so far used RustFS on the same machine, so no network sits in the path. The R2 phase will run the same suites against a remote bucket. To keep those numbers readable, each R2 campaign starts with a network baseline (upload/download of a known file, small-GET latency), and every suite counts its GET/PUT requests. The comparison then separates the network's cost from the engine's.
- **Goal reached: 1.29 billion rows inside 10 GB** (GHCN 1998–2025, 7.9 GB with TPC-H; see §6.6). Original plan: At ~2.7 bytes per bronze row, the 6.5 GB reserved for one writer's lakehouse fits ~1.3 billion bronze rows with today's layout, and more if sorting before writing pays off as it did in phase 1. The benchmark runs first on the current 742 M rows; after the layout suite (B6), `r2` grows by years until it fills the budget, and the suites run again. The Cloudflare R2 run comes last, after every local phase.
- **Scale `local`** will be the whole GHCN history, 1750–2025 (~14.4 GB to download, ~19 GB of lakehouse). At 5 M rows/s, ingestion would need far more data than GHCN has to reach 30 minutes, so the history's size is the limit.

## 7. What surprised me

- **Sorting beat partitioning, but partitions still earned their keep.** Every gold table started partitioned by month, the textbook layout for time series. The first B6 round made partitions look useless: 190 M rows came to 0.38–0.73 GB, so each month held 2–4 MB, and the file size knob did nothing. Sorting the data was the big win: half the storage, a 37% faster yearly count. So we tested sort-only tables expecting to drop partitions, and the numbers said no. Without the monthly partition, the same sorted table answered period-filtered questions 60–80% slower (Q2: 378 → 679 ms). Trino still prunes whole months from the manifest, even when they are tiny. The rule we ended with: sort first; keep a time partition when queries filter by period, or when it serves the writes; never partition without sorting. A yearly partition without a sort order made the yearly count take 197 s; sorted, it took 0.49 s.
- **A sleeping laptop looks like a distributed-systems bug.** Trino's `ABANDONED_TASK` turned out to be macOS idle sleep freezing the Docker VM, twice: once mid-run, once in a gap between runs. The clue was query IDs lagging the log clock.
- **Materialized views have to match the query's shape, not its intent.** StarRocks' wide join MV served none of the SQL Cube generates. A boring copy of each table served all of it.

- A single node inside a VM on macOS: compare engines with each other, not with absolute numbers elsewhere.
- One dataset shape (append-heavy time series).
